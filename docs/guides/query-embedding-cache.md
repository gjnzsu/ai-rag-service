# 第一阶段：查询 embedding 缓存设计与实验

更新日期：2026-09-19。本文记录第一阶段的设计决策、当前实现和实验边界。

## 设计目标与分阶段范围

先验证重复查询能否减少 embedding 外部调用。查询向量只由模型及输入处理决定，不包含 Jira 当前状态或图关系，因此它是较容易控制失效边界的缓存对象。

| 阶段 | 缓存对象 | 当前决定 |
| --- | --- | --- |
| 第一阶段 | 查询 embedding | 已实现可选的进程内精确匹配缓存，默认关闭 |
| 第二阶段 | Graph 检索结果 | 尚未实现；需考虑 snapshot_id、方向、过滤条件及权限范围 |
| 后续 | 最终回答／语义答案 | 尚未实现；需考虑证据版本、权限、提示词、模型及误匹配风险 |

查询向量命中后，后续仍读取本次请求选定的索引和快照。缓存不会自动更新业务数据：Jira 更新后，Graph PoC 仍需重建并发布快照，才能检索到新状态。

## 改动组件与职责

| 组件 | 职责 |
| --- | --- |
| `app/query_embedding_cache.py` | `QueryEmbeddingCache` 管理键值、LRU、TTL、并发访问和统计；`embed_query()` 处理开关与模型服务身份 |
| `app/retrieval/vector.py` | `ChromaVectorRetriever.search()` 在生成查询向量前查缓存，随后继续查询 Chroma；覆盖 Vector/Hybrid 路径 |
| `app/api/graph.py` | 为 `SnapshotSearch` 提供带缓存的查询 embedding 回调；命中时无需创建 OpenAI 客户端 |
| `app/config.py`、`.env.example` | 声明开关、容量和 TTL |
| `scripts/evaluate-query-embedding-cache.py` | 对比关闭、冷缓存、热缓存条件下的 embedding 调用数和耗时 |

## 一次查询如何执行

1. 接收实际需要发送给 embedding API 的文本。
2. 缓存关闭时，直接调用原 embedding 路径。
3. 缓存开启时，生成完整键并检查条目是否存在、是否过期。
4. 有效命中时返回已保存向量的副本；未命中时调用 API，符合缓存条件的成功向量写入缓存。
5. 用得到的向量继续检索本次请求的数据；需要回答时，继续生成回答。

这是一种 cache-aside 方式：先查缓存，缺失时计算并写入。只省掉查询向量生成，不缓存检索结果或答案。

## 缓存键和值：匹配输入，而不是比较向量

可以先把缓存理解成“输入标签 → 上次生成的向量”。实际结构是：

```text
key   = SHA-256(JSON([隔离范围, 模型服务身份, 模型, 维度, 输入处理版本, 实际文本]))
value = (过期时间, 不可变向量 tuple)
```

模型服务身份包含 endpoint 和凭证的 SHA-256 指纹。对整个标签再计算哈希，得到固定长度的键；哈希不是语义相似度，也不是 embedding 向量。

| 键字段 | 为什么需要 |
| --- | --- |
| 隔离范围 | 避免跨数据范围复用；Vector 使用 `vector`、索引路径、collection，Graph 使用 `graph`、site、project、account_scope |
| 模型服务身份 | 隔离不同 endpoint 和凭证环境 |
| 模型及维度 | 避免模型配置改变后继续使用不兼容的向量 |
| 输入处理版本 | 文本处理规则改变时，可主动划分新的缓存空间 |
| 实际文本 | 确定本次模型输入是否与已缓存输入完全一致 |

假设其他字段相同、条目有效且未被淘汰：

| 实际发送文本 | 行为 |
| --- | --- |
| 第一次：哪些任务阻塞模型发布？ | 未命中，调用 API 并保存向量 |
| 第二次：哪些任务阻塞模型发布？ | 精确命中，返回上次向量的副本 |
| 第三次：模型发布被哪些任务卡住了？ | 文本不同，重新调用 API |
| 第四次：原句末尾多一个空格 | 文本不同，重新调用 API |

即使不同文本最终生成的向量恰好相同，也分别缓存。查询前不会先调用 embedding API 再比较向量，否则已经付出了希望省掉的调用成本。意思相近的输入能否共享属于后续语义缓存设计，需要另外评估相似阈值和错误复用。

命中保证的是“返回之前保存的数值”，不保证“重新调用 API 必然生成逐值完全相同的数值”。当前设计允许在配置和范围一致、TTL 有效时复用已生成的表示。若服务端在同一模型名称下更新模型，键无法自动感知；需要通过配置版本变化或重启清空缓存，TTL 也会限制旧条目的复用时长。

普通检索和 Graph 共用同一个缓存组件，但范围前缀不同，当前不会跨这两条路径共享条目。Graph 的键不含 snapshot_id，因为查询表示不依赖 backlog 快照；检索仍由 manifest 固定到本次快照。

## 存储与生命周期：进程内实现

本阶段没有引入 Redis。数据保存在 RAG 服务进程内，由 Python 标准库实现：

- `OrderedDict` 保存条目及访问顺序；命中移到末尾，超过容量时淘汰最久未使用的条目。
- 单调时钟记录过期时间，避免系统时间校准影响 TTL；读取不会延长有效期。
- `Lock` 保护共享缓存及计数器；外部模型调用在锁外执行，避免慢请求阻塞其他缓存访问。
- 内部向量保存为 tuple，对调用方返回 list 副本，避免调用方修改缓存内容。

缓存实例在模块加载时创建，跨请求保留；服务重启清空，每个 worker／实例各有一份。条目数上限控制容量，不是精确的字节内存上限；没有持久化、跨进程共享或后台清理任务。

选择进程内缓存是为了先验证命中率和调用收益，不增加独立组件的部署维护工作。如果后续多实例之间重复计算明显，再评估 Redis 共享缓存；Redis 不会自动带来语义匹配能力，仍需单独决定键和失效策略。

## 范围与启用

Vector/Hybrid 查询和 Graph 语义起点查询已接入进程级缓存。文档入库、图快照构建、检索结果、rerank 和最终回答不缓存。Graph 显式 issue key 查询沿用原路径。

在服务启动环境或 `.env` 中设置并重启服务：

```dotenv
QUERY_EMBEDDING_CACHE_ENABLED=true
QUERY_EMBEDDING_CACHE_MAX_ENTRIES=1024
QUERY_EMBEDDING_CACHE_TTL_SECONDS=900
```

默认关闭；关闭后每次调用原 embedding 路径。容量和 TTL 在进程启动时读取，重启清空缓存。多 worker/多实例分别保存自己的缓存。

## 缓存约定

- 使用有锁的进程内 LRU，最多 1,024 条；从成功写入开始保留 900 秒，读取不延长 TTL。过期数据在访问或后续写入时清理，无后台线程。
- 对完整键的 JSON 表示计算 SHA-256；键包含范围、服务 endpoint、凭证指纹、模型、维度、预处理版本以及实际发送的输入。内存键和日志不保存查询原文或凭证明文。
- Vector 范围为索引路径及 collection；Graph 范围为 site、project、account_scope。Graph 不包含 snapshot_id，因此同一授权范围的不同快照可以复用向量。未来加入用户级授权时，应同步将服务端确定的授权范围纳入键。
- 当前模型为 `text-embedding-3-small`、默认 1,536 维、输入处理版本为 `identity-v1`。大小写和空白不同的实际输入不共享；若上游处理输入，则以处理后真正发送的文本为准。模型或输入处理改变时必须同步修改这些标识。
- 仅缓存维度匹配且数值有限的成功向量。上游异常原样交给原调用链处理；缓存读写异常回退，不因为写缓存失败而重复请求上游。返回值复制，调用方无法修改已缓存向量。
- 外部调用不持锁；并发冷请求允许重复调用上游，第一阶段不做 single-flight。因此命中数等于直接省掉的调用数，但不能假设所有同一时刻的重复请求只调用一次。
- 命中后仍查询当前 Chroma/Graph 数据，并执行后续回答生成。这不是权限校验机制，也不是答案缓存。

## 已运行的实验（2026-09-19）

同一固定问题顺序查询三次；先关闭缓存，再使用空缓存。真实实验总共发出四次 embedding 请求，无检索或 LLM 回答调用。

| 条件 | embedding 请求数 | 各次耗时（ms） |
| --- | ---: | --- |
| 关闭缓存 | 3 | 2932.325 / 976.549 / 962.450 |
| 开启缓存 | 1 | 832.876 / 0.256 / 0.175 |

开启组命中率 2/3，减少两次外部调用。真实 API 的三次直接响应向量并非逐值完全一致，缓存组返回的是首次成功响应的副本。样本很小，关闭组首次请求还含连接预热成本；这些结果只证明查询向量可复用，不能外推端到端 RAG 收益或生产命中率。

原始记录：[真实调用](../evaluation/query-embedding-cache-live.json)、[20 ms 模拟调用](../evaluation/query-embedding-cache-simulated.json)。

复现实验（项目 Python 环境中）：

```powershell
python scripts/evaluate-query-embedding-cache.py --output docs/evaluation/query-embedding-cache-simulated.json
python scripts/evaluate-query-embedding-cache.py --live --output docs/evaluation/query-embedding-cache-live.json
```

第二条使用现有 OpenAI 配置并产生四次付费调用。脚本每次创建独立空缓存。生产接入另有测试覆盖：跨 Vector retriever 实例复用但仍查询 Chroma；Graph 跨请求/快照复用、account_scope 隔离。

## 服务级验收方式

1. 单 worker 启动已有服务，固定数据快照、模型和查询集。分别关闭/开启缓存，每轮重启，顺序重放相同的问题；同时包含重复问题、不同问题和显式 issue key。
2. 观察 `query_embedding_cache` 结构化日志的 `status=hit/miss` 和 `elapsed_ms`，按 worker 统计命中数及成功请求命中率；`query_embedding_cache_error` 表示缓存回退。不要将未使用 embedding 的请求计入分母。
3. 从调用方另行测量 `/retrieve` 或 `/query` 总耗时，冷启动和热查询分别汇总 p50/p95。缓存日志只涵盖 embedding 边界；本次未执行服务端到端延迟实验。
4. 确认命中后仍获取当前检索证据；切换快照或更新索引后复用向量，但读取对应的新索引数据。

后续是否引入共享缓存或 Graph 结果缓存，应依据真实流量重复率、节省的调用数和端到端延迟决定。
